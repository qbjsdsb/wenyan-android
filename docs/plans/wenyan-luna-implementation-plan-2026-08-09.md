# 文研 Android：面向南师大文学专业课复习的产品重构与 Luna 实施计划

> 调研与审计日期：2026-08-09  
> 代码基线：`qbjsdsb/wenyan-android`，`main@c1df65e860bc1e9f9deb046d63f4a05ac14f2883`  
> 当前发布基线：文档标注 v0.9.43、数据库 v10、seed v2.26.0  
> 输入材料：当前仓库、项目历史约束、`tools.zip` 历史工作站快照、南师大招生信息、学习科学研究、同类产品与开源项目

## 一、结论先行

如果我来继续做这个软件，我不会把它做成“又一个资料库”或“安卓版 Anki”，而会把它收敛成：

**一套离线优先、以南师大文学专业课为目标、每天自动组织“记忆—答题—写作—复盘”的个人备考教练。**

当前项目最值得保留的是：

- 已有 1101 个知识点、564 道题、Room 数据库、FSRS-6 调度、错题本、考试倒计时和较完整的自动化测试；
- Kotlin/Compose/Hilt/Room 的多模块骨架是可继续演进的，不需要推倒重来；
- 已经形成“科目—章节—知识点”的稳定 ID 体系，用户进度也被认真保护。

当前项目最需要纠正的是：

- **内容数量大于内容可信度。** 1101 个知识点中仅 201 个有非“其他”的教材来源；516 个高频知识点中只有 39 个有可识别来源。loader 却会把大量历史内容标成 `TEXTBOOK_NATIVE / VERIFIED`，这会把“文本可读”误写成“出处已核验”。
- **复习引擎强于学习闭环。** 今日队列藏在卡片页，首页仍从知识浏览开始；用户没有一个稳定、跨重启不乱序的每日计划。
- **调度粒度过粗。** 一个知识点拆成多张 sibling 卡，但共享知识点级 FSRS 记录，只有第一张评分真正参与调度。它能避免稳定性虚高，却不能反映“定义会了、比较不会、论述不会”的差异。
- **输出训练不足。** 真题页偏答案浏览；909 条 `writing_materials` 全部来源为“其他”，没有标题、知识点关联或真正的写作素材类型，而且没有被完整接入用户学习流程。
- **610 专业写作尚未成为一等功能。** 现有 `AnswerTemplate`、`TemplateFill`、`AiGradingRecord`、`WritingMaterial` 表大多处于未接线状态，正好可以复用来做写作工作台。
- **历史工具包不可直接合并。** `tools.zip` 解压约 404 MB，含大量 Windows 绝对路径、OCR 中间产物、缓存、JDK/Gradle/SDK 和历史脚本；旧“交叉验证”数据 909 条里没有真正的多来源知识点，旧真题 OCR 还混有广告/扫描器水印。它只能作为线索和原始证据库存，不能作为当前构建系统。

因此正确顺序不是先美化页面，而是：

1. 建立可审计的内容流水线；
2. 把复习单位从“整个知识点”细化为“可独立回忆的学习单元”；
3. 做稳定的每日计划和真正的“今日”首页；
4. 接通真题作答、610 写作和复盘；
5. 最后才做提醒、统计、AI 辅助和更多内容批次。

| 写作素材显式关联知识点 | 0 / 909 | 无法服务“学完知识点立刻做输出” |

这些数字说明，短期不能用“总条目数”当完成度。应同时显示三种覆盖率：

- **内容覆盖**：是否已经有可学习文本；
- **来源覆盖**：是否有页码/原卷/版本等可核验出处；
- **训练覆盖**：是否有卡片、真题或写作任务能检验输出。

### 2.3 `tools.zip` 的正确定位

`tools.zip` 共 368 个归档文件，解压约 403,964,636 字节。主要包含 OCR 输出、并行 OCR 测试、MinerU/图片管线测试、下载文件、缓存、SDK/JDK/Gradle 和脚本。旧 manifest 有 208 个条目，其中 172 完成、36 跳过，路径全部是 `D:\...` 风格。

正确使用方式：

- 将它视为“历史原始资料索引＋失败案例库”；
- 提取 source manifest、可核验页码、OCR 噪音词和旧 ID 映射；
- 用它生成回归样本，例如广告、水印、页眉页脚误识别的检测用例；
- 原教材/PDF 若受版权保护，只保留在个人本地资料目录，不提交到公开仓库。

禁止做法：

- 不把整个 zip 解压进仓库；
- 不复用其中的 JDK、Gradle、SDK、缓存和 `__pycache__`；
- 不继续依赖 Windows 绝对路径；
- 不把旧 `ocr_status=VERIFIED` 当作人工核验结论；
- 不把 LLM 生成的分析、页码、原题措辞或引用直接发布为官方内容。

## 三、考试口径与产品边界

南师大 2026 专业目录应作为当前可执行基线；中国现当代文学方向的专业课结构已经进入“610 专业写作＋801 文学基础”的组织方式。学校又发布了 [2027 年硕士招生自命题科目调整公告](https://yjszs.njnu.edu.cn/info/1073/17512.htm)，并说明调整信息持续更新。因此软件不能把“2027 科目与参考书已最终确定”写死，应做年度考试方案版本化，并在最终招生目录发布后再切换默认方案。官方的 [2026 中国现当代文学专业目录页](https://yz.njnu.edu.cn/pages/sszsml/sszsml_zyjs.jsp?nd=2026&yxdm=001&zydm=050106) 可作为当前元数据来源。

项目内容边界继续遵守原有决定：

- 丁帆《中国新文学史》上、下册继续分批完善；
- 聂珍钊《外国文学史》只使用用户已经提供的指定版本，不混入其他教材冒充同版；
- 袁世硕三册当前暂停，不因为“补全率”而擅自恢复；
- 2024/2025 年 805 真题只允许从原卷或用户确认的可靠版本录入，不猜题、不补全不存在的题干；
- 旧 610/801/805/806/807 的科目代码历史必须按年份保存，不能靠当前科目名覆盖历史。

产品第一阶段不做：

- 通用笔记编辑器；
- 云端账号、服务器和多端同步；
- 社区题库和资料交易；
- 重新上线全屏知识图谱；
- 自动抓取并发布网上考研资料；
- AI 一键生成“官方答案”。

这些功能都比“每天能否完成一次高质量复习”优先级低，而且会增加维护费用、版权风险和内容污染面。

## 四、学习机制：为什么这样设计

学习科学的共识对这个项目很明确：不能让用户一直阅读摘要，必须持续尝试从记忆中提取、得到反馈、隔一段时间再提取。Dunlosky 等人的综述把练习测试与分散练习评为高效策略；Karpicke 与 Blunt 的实验显示，主动提取对有意义学习的效果高于仅做概念图；successive relearning 研究强调“达到回忆标准后，在后续分散场次再次学会”。相关来源见 [Dunlosky et al.](https://pubmed.ncbi.nlm.nih.gov/26173288/)、[Karpicke & Blunt](https://pubmed.ncbi.nlm.nih.gov/21252317/) 和 [Rawson & Dunlosky](https://pubmed.ncbi.nlm.nih.gov/23088488/)。课堂研究综述也支持带反馈的低风险提取练习，见 [Agarwal et al.](https://pdf.poojaagarwal.com/Agarwal_etal_2021_EDPR.pdf)。

| 学习原则 | 在文学专业课中的含义 | 软件机制 |
| --- | --- | --- |
| 提取练习 | 先说出定义、要点、比较和论证，再看材料 | 卡片先答后揭示；真题先写提纲；知识页提供“30 秒回忆”入口 |
| 分散练习 | 同一考点隔天、隔周重新输出 | FSRS 调度原子学习单元，不按整章一刀切 |
| 达标后再学习 | 一次答对不等于真正掌握 | 核心单元跨至少两个场次成功，才进入稳定状态 |
| 带反馈练习 | 知道漏了哪个关键词、证据或逻辑环节 | 答案核对表、评分量规、错因标签，而不是只显示“对/错” |
| 交错练习 | 相近概念要放在一起辨析 | 对比题与不同科目/时期轮换；不是完全随机打散。交错学习的优势常来自类别间的辨别对照，见 [Birnbaum et al.](https://pubmed.ncbi.nlm.nih.gov/23138567/) |
| 输出迁移 | 会背定义不等于会写名词解释、简答和论述 | 每个知识点连接至少一种考试输出任务 |
| 元认知校准 | “看着熟”经常被误当作“会答” | 展示预测掌握度与真实作答表现的差距 |

不应该只给一个“掌握度 83%”。文学专业课至少应显示三个维度：

1. **见过**：内容覆盖与学习进度；
2. **记得**：FSRS 预测、最近回忆表现；
3. **写得出**：名词解释/简答/论述/写作的最近输出表现。

| 项目/产品 | 可借鉴部分 | 不应照搬的部分 | 许可证/风险 |

| [Moodle Rubric](https://docs.moodle.org/502/en/Rubrics) | 评分标准＝维度 × 成就等级，每项可给反馈 | 不引入课程管理、教师角色和服务端 | 用量规思想做 610 写作自评/AI 辅评 |
| Android 官方架构 | Room 作为本地真相源、Repository/Flow、WorkManager 做持久后台提醒 | 不因 AI 或内容更新让 UI 直接访问网络 | 继续沿用当前离线架构；参考 [Android offline-first 指南](https://developer.android.com/topic/architecture/data-layer/offline-first) |

## 六、目标产品信息架构

顶层导航改为四个入口：

| 顶层页 | 解决的问题 | 包含内容 |
| --- | --- | --- |
| 今日 | 我今天具体该学什么？ | 倒计时、预计用时、今日任务、追赶提示、一键继续、完成总结 |
| 知识 | 这个考点到底是什么，出处在哪？ | 学科框架、章节进度、分层知识页、来源、对比关系、相关真题 |
| 训练 | 我能不能在考试形式下写出来？ | 卡片、名词解释/简答/论述、610 写作、错题、专项冲刺 |
| 我的 | 我的进度是否可信，数据能否安全保留？ | 三维掌握度、复习统计、薄弱点、设置、提醒、导入导出、AI 配置 |

现有卡片、错题、设置模块不立即删除。先在新导航中包一层入口，确认功能等价后再移除旧顶层目的地，避免一次性大改导航。

### 6.1 “今日”页的最小闭环

每日任务按以下顺序生成，但一旦生成就持久化，不因重启、重新订阅 Flow 或跨过午夜而静默换序：

1. 到期复习：FSRS 到期学习单元；
2. 遗忘修复：最近 Again、错题、leech；
3. 新内容覆盖：按考试剩余天数、考频、来源状态和学科轮换选择；
4. 输出训练：至少一个名词解释/简答提纲；
5. 写作任务：按周计划加入 610 微写作、提纲或整篇限时写作；
6. 结束复盘：展示漏项、错因和下一次安排。

当天再次进入时，只读取已有 `DailyPlan`。如果设置、考试日期或内容 seed 发生变化，默认“明天生效”；用户明确点击“重建今日未完成任务”才重新计算。日期变化后，昨日未完成项进入“昨日遗留”区域，由用户选择带入、跳过或专项处理，不自动插队。

### 6.2 知识点页面的五层结构

每个知识点不再只是长文阅读，而是同一内容的五种学习视图：

1. **30 秒回忆**：一句核心结论＋关键词遮挡；
2. **2 分钟答题骨架**：3–6 个有序要点；
3. **考试表达**：名词解释、简答或论述的组织方式；
4. **理解与辨析**：时代背景、作品、文学史意义、争议观点、易混概念；
5. **证据与来源**：教材版本、页码、原卷来源、审校状态和关联内容。

关系不再由“同科目＋共享标签”单一推断。至少支持：

- `COMPARE_WITH`：对比；
- `INFLUENCES / INFLUENCED_BY`：影响关系；
- `PART_OF`：属于思潮/流派/阶段；
- `EVIDENCE_FOR`：作品或材料支持某论点；
- `EXAM_VARIANT`：同一考点的不同问法。

暂时只在知识页用“关联卡片/路径”展示，不恢复图画布。

### 6.3 训练页

训练页包含四种明确模式：

- **快速回忆**：原子学习单元＋FSRS；
- **真题作答**：先输入关键词/提纲，再核对答案框架和漏项；
- **610 写作**：审题、立意、提纲、限时正文、自评量规、可选 AI 反馈；
- **错题修复**：按错因而不是只按题目堆积。

错因枚举建议：`MEMORY_GAP`、`CONCEPT_CONFUSION`、`MISREAD_PROMPT`、`WEAK_STRUCTURE`、`WEAK_EVIDENCE`、`TIME_CONTROL`、`EXPRESSION`。这比单纯“Again”更能指导下一次任务。

### 6.4 610 写作工作台

写作工作台应优先复用已存在但未接线的表：

- `AnswerTemplateEntity`：存内置题型模板和评分量规；
- `TemplateFillEntity`：保存提纲、分段字段、正文、字数和草稿；
- `AiGradingRecordEntity`：保存可选 AI 批改结果；
- `WritingMaterialEntity`：改造成真正的论点、理论、作品证据、引文线索和表达模板库。

MVP 工作流：

1. 选择真题/模拟题；
2. 3–5 分钟审题并写中心论点；
3. 写分论点与证据卡；
4. 选择 10 分钟提纲、30 分钟微写作或完整限时写作；
5. 按“立意、结构、理论、文本证据、分析、语言、时间”自评；
6. 对照人工审校框架；
7. 可选调用 AI，只让它按固定 JSON 量规给反馈，不让它改写成所谓标准答案；
8. 把弱项生成后续任务。

先做本地规则反馈：字数、段落、论点字段是否为空、证据数量、是否引用了已审校知识点。这部分零 API 成本，也最可重复。AI 反馈必须记录模型、prompt 版本、引用的 source ID、token 用量和生成时间，并显式标注“AI 辅助意见”。

## 七、调度与数据模型

### 7.1 原子学习单元

当前 `MemoRecord` 以 `knowledgePointId` 为主键，而一个知识点会拆成多张 sibling 卡。建议新增 `LearningUnit`，不修改既有知识点 ID：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定 ID，如 `kp_00001:core:0`；不得使用内容 hash，文案修订不能让进度丢失 |
| `knowledge_point_id` | 继续指向原知识点 |
| `unit_type` | `CORE`、`KEYWORD`、`SEQUENCE`、`COMPARE`、`EVIDENCE`、`EXAM_OUTLINE` |
| `position` | 同类单元稳定顺序 |
| `prompt` / `answer` | 可独立提取的最小问题与核对内容 |
| `source_version` | 单元来自哪个已发布内容版本 |
| `active` | 内容被替换时停用，不物理删除历史记录 |

另建 `LearningUnitRecord` 保存每个单元的 FSRS 状态。旧 `memo_records` 不删除；升级时只把知识点级旧进度复制到 `:core:0`，其余新单元保持 NEW。这样既不把用户进度复制得虚高，也不会丢失旧记录。`review_logs` 增加可空的 `learning_unit_id`，保留原 `point_id` 方便历史统计。

### 7.2 每日计划

新增：

```text
daily_plans
- id / plan_date / created_at / exam_scheme_year
- settings_snapshot_json / content_version / status

daily_tasks
- id / plan_id / order_index / task_type
- content_id / learning_unit_id / estimated_minutes
- state / carried_from_task_id / created_at / completed_at
```

同一天任务的稳定排序键建议为：

```text
bucketRank
→ overdueDays DESC
→ predictedRetrievability ASC
→ examFrequencyRank
→ recentWeakness DESC
→ subjectRotationRank
→ stableId ASC
```

其中 FSRS 到期任务永远优先于“为了凑覆盖率”的新内容。考试计划只调节新内容速度和输出训练比例，不随意提前全部未到期卡。

新内容日配额可按以下思路计算：

```text
待覆盖且允许学习的单元数 ÷ max(考试前剩余有效学习日 - 30, 1)
```

再应用用户上限和最低值。若按当前速度无法在考前完成，显示“计划不可行”与三个明确选择：增加每日时间、降低低频范围、延长追赶期。不要后台悄悄提高任务量。

### 7.3 内容可信度模型

至少区分两个维度：

**内容审校状态**

- `REVIEWED`：来源、文本和映射已经人工审校；
- `LEGACY_UNVERIFIED`：历史内容可学习，但具体出处尚未补齐；
- `AI_DRAFT`：模型生成草稿，只能在编辑/审校工具里出现；
- `REJECTED`：确认不应发布。

**真题真实性**

- `OFFICIAL_ORIGINAL`：官方/原卷扫描；
- `USER_CONFIRMED`：用户确认的可靠试卷；
- `SECONDARY_RECOLLECTION`：回忆版或二手整理；
- `UNKNOWN`：无法判断。

不要再让 `ocr_status=VERIFIED` 同时承担“文字识别完成”和“学术来源已审校”两种含义。

### 7.4 建议的数据库版本顺序

当前基线是 v10；若实施时主分支已变化，则按实际版本顺延，不能覆盖已有迁移编号。

- **v11：内容溯源**  
  为知识点/真题/写作素材增加审校状态；为真题增加真实性状态；为写作素材增加标题和 `related_point_ids`；扩展 `data_sources` 的书名、版次、起止页、校验值、审校备注。
- **v12：学习单元**  
  新增 `learning_units`、`learning_unit_records`；给 `review_logs` 增加可空 `learning_unit_id`；迁移旧知识点级进度到 core 单元，旧表继续保留。
- **v13：每日计划**  
  新增 `daily_plans`、`daily_tasks`；所有任务状态写入 Room。

每次版本升级必须同时交付：实体、DAO、migration、导出的 schema JSON、从上一版本升级的 instrumentation test、从已发布旧版本链式升级的测试、用户记录不丢失断言。

## 八、可审计内容流水线

`seed_data.json` 应从“手工维护的巨大源文件”变成构建产物。建议仓库结构：

```text
content/
  schema/
  manifests/              # 只存来源元数据、版本、页码范围、sha256、权利说明
  drafts/                 # AI/OCR 草稿，永不直接进入 app
  reviewed/               # 人工审校后的结构化内容
  published/              # 可进入正式 seed 的快照
tools/content_pipeline/
  import_legacy.py
  normalize.py
  validate.py
  build_seed.py
  audit_report.py
```

原教材、整本 PDF 和可能受版权保护的扫描件不提交公开仓库。manifest 只记录个人本地 source key、书名、版本、页码、文件 sha256 和允许用途。构建正式 seed 只能读取 `published/`。

CI 必须执行：

- JSON Schema 校验；
- ID 唯一与稳定；
- 知识点/真题/来源关联无悬空；
- 已发布条目数量不能无说明下降；
- 已存在 ID 不能被重排或复用；
- `AI_DRAFT` 不能进入 published；
- 新增 `REVIEWED` 条目必须至少有一个有效 source；
- 题干、页码、年份不得由模型凭空补齐；
- 检测“扫描全能王、微信、淘宝、公众号、店铺、加 QQ”等 OCR 广告噪音；
- 生成按学科、考频、年份、题型和来源状态的审计报告；
- `build_seed.py --check` 验证仓库内 seed 与 published 输入可重复生成。

内容发布采用 ratchet，不要求一夜之间把 1101 条全审完：

1. 建立 201 条已有来源内容的真实基线；
2. 优先补高频 516 条，先做当前 801/610 需要的知识与输出映射；
3. 再补中频和真题关联；
4. 最后处理低频与历史扩展。

任何批次都不得为了提高百分比而把“其他”改成某本教材，除非实际核对过版本和页码。

## 九、Luna 可执行的 PR 路线图

OpenAI 官方把 GPT-5.6 Luna 定位为适合明确、可重复和高吞吐任务的低成本模型，而不是模糊的大型架构探索；官方也建议从满足要求的最低 reasoning effort 开始，复杂任务再提高。参见 [Codex 模型说明](https://learn.chatgpt.com/docs/models)。因此这套路线图把架构决定预先固定，每个 PR 只做一件事。

### PR-00：冻结基线与统一项目真相

**目标**：先让文档、代码和测试基线一致，不改变用户行为。

**工作**：

- 核对 `docs/00-STATUS.md`、`AGENTS.md`、`SESSION_LOG.md` 的版本、测试数量、当前 commit；
- 新增 `docs/architecture/current-system.md`，记录模块、导航、数据表、seed 统计和关键不变量；

- 建立 `docs/decisions/`，记录“离线优先、ID 不变、AI 不发布官方内容、暂不做图谱”。

**验收**：只改文档；状态数字能由命令复算；`git diff --check` 通过。

### PR-01：内容审计工具与 CI 门禁

**目标**：先检查现有 seed，不改变 app 读数或 UI。

**工作**：

## 十、Luna 的省钱执行法

### 10.1 模型与工作粒度

在可选模型的本地/IDE 场景使用：

```bash
codex -m gpt-5.6-luna
```

官方说明中 Luna 最适合“明确、可重复”的工作。因此建议：

- 文档、schema、机械映射、单一 DAO/UI 组件：Low/Light；
- 普通功能 PR、测试修复：Medium；
- 单次数据库 migration 或确定性队列：High，但仍只给一个明确任务；
- 不用 Ultra，不开并行 agent 修改同一仓库；省下来的冲突处理通常比并行速度更值钱。

每个 Luna 工单控制在：

- 一个用户可见行为或一个基础设施目标；
- 主要修改不超过约 8 个手写源文件（生成 schema/测试 fixture 不计）；
- 手写 diff 理想为 300–800 行；
- 一次最多一个数据库版本迁移；
- 先跑目标模块测试，阶段 PR 再跑全量测试。

如果 Luna 开始同时提议重写导航、数据库和 seed，立即停止并把任务再拆小。

### 10.2 每个工单都要附带的上下文

不要让 Luna 每次重新“研究整个项目”。每个 PR 固定提供：

1. 当前 commit 和数据库/seed 版本；
2. 目标与不做什么；
3. 允许修改的模块/文件；
4. 必须保持的不变量；
5. 数据迁移与回滚要求；
6. 验收命令和必须新增的测试；
7. 已知大文件，要求提取组件而不是继续堆代码。

### 10.4 第一个 Luna 工单

不要一上来做首页。第一个工单应是 PR-00/PR-01：

```text
先复算知识点、真题、写作素材、来源覆盖、高频来源覆盖、分值、显式关联和 OCR 噪音统计。
新增 schema、audit 脚本、测试与 CI 检查；同一输入的报告必须确定性一致。
当前异常可进入 baseline，但新增异常必须让 CI 失败。

不要修改 seed 内容，不修改 Room，不修改 Compose UI，不引入 OCR、LLM 或大型 Python 依赖。
```

这是最适合 Luna 的任务：目标明确、结果可机器验证，而且能为后续所有内容工作省掉大量返工。

## 十一、验收指标

### 产品闭环

- 冷启动后 1 次点击开始今日任务；
- 同日重启/进程死亡后任务集合、顺序、完成状态不变；
- 每个已排期知识点至少能进入“回忆”和一种“输出”任务；
- 610 写作无网络也能完成提纲、正文、自评与保存；
- 用户能看到内容是已审校、历史未核验还是 AI 草稿。

### 内容质量

- 新增 `REVIEWED` 内容 100% 有 source；
- 新增真题 100% 有真实性状态和来源说明；
- `AI_DRAFT` 进入正式 seed 的数量为 0；
- 既有 ID 无静默删除、重排或复用；
- 悬空引用、重复 ID、OCR 广告新增量为 0；
- 来源覆盖按批次单调上升，不用伪来源换百分比。

### 学习效果的代理指标

- 到期任务完成率和逾期天数；
- Again 后 7/14 天修复率；
- 同主题“看过→记得→写得出”的转化；
- 真题提纲漏项数趋势；
- 610 写作各 rubric 维度趋势，而不是只看 AI 总分；
- 计划不可行警告是否减少。

### 工程质量

- 当前测试基线不下降；
- 每次 DB 变更都有迁移链测试；
- debug/release 构建保持；
- seed 可重复生成；
- 不新增超大 ViewModel/Screen；
- 不因失败升级而回退到 destructive migration。

## 十二、最终优先级

如果时间和预算有限，只做前八个 PR，顺序也不要换：

1. 内容审计；
2. 可信度与来源；
3. 原子学习单元；
4. 持久每日计划；
5. 今日首页；
6. 分层知识学习；
7. 真题训练；
8. 610 写作。

提醒、漂亮统计、AI 批改、知识图谱都可以晚一点。真正能提高专业课复习效果的，不是更多按钮，而是每天稳定完成这条链：

**先回忆 → 再核对 → 做真题输出 → 做写作迁移 → 记录错因 → 在合适的时间再来一次。**

只要内容出处诚实、任务顺序稳定、用户数据不丢，这个项目就不需要服务器，也不需要昂贵模型，仍然可以成为一套很强的个人文学考研工具。
