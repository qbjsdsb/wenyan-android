## 3. 永久不变量

### 3.1 数据和用户进度

- 既有 knowledge point、exam question、chapter ID 不删除、不重排、不复用。
- seed 内容更新只能采用追加或有明确证据的勘误；不通过改 ID 绕过审计。
- 不清空或覆盖 memo_records、FSRS 状态、review_logs、错题本、练习记录、写作草稿、设置和 AI 配置。
- Room 变更必须有显式 migration、导出的 schema 和已发布旧数据库升级测试；禁止 destructive migration。
- seed 导入不得让用户进度回到 NEW，也不得用新内容覆盖已有复习字段。

### 3.2 内容可信度

- AI/OCR 输出只能进入草稿或待审校状态，不能自动成为 REVIEWED。
- 未经核验的文本不能包装成教材原文、正式页码、学者原话或官方真题。
- AI_DRAFT 或 REJECTED 不得进入正式发布内容。
- “其他”“未知”“待补”“无”等值不能作为可展示的书名或页码证据。
- 2024/2025 年 805 真题只依据原卷或用户确认的可靠版本；不得补写猜测的题干、分值和答案。
- 丁帆《中国新文学史》上下册继续分批核对；聂珍钊只使用用户指定版本；袁世硕三册保持暂停，除非用户明确恢复。

### 3.3 工程和范围

- 先做可复算的内容质量门禁，再做来源数据层、学习单元、每日计划和 Today UI。
- 不把逻辑继续堆进 CardsScreen.kt、CardsViewModel.kt、KnowledgePointDetailScreen.kt、SeedDataLoader.kt 等大文件。
- 不恢复全屏知识图谱；当前使用章节树和显式关联。
- 不引入云账号、服务器、多端同步、社区、资料交易或 AI 官方答案。
- tools.zip 只作为历史证据与失败样本索引，不能整体解压到仓库；不得提交其中的教材、SDK、JDK、Gradle、缓存、日志、__pycache__ 或 Windows 绝对路径。

## 4. Luna 工单协议

### 4.1 常规单工单模式

每个 PR 只完成一个明确目标，固定遵循以下流程：

1. 从最新已合并 main 新开独立分支；
2. 只读读取指定文件并报告当前基线、改动面、风险和测试；
3. 用户明确允许后才实施；
4. 先加入能证明目标的失败测试或确定性检查，再做最小实现；
5. 完成后进行本地自审，检查 diff、ID、用户数据和测试证据；
6. 只提交当前工单范围，创建 Draft PR；
7. CI 全绿并完成真机或人工验收后才允许 Ready 和合并；
8. 合并后关闭当前对话，下一工单重新从最新 main 开始。

任何工单都不得直接推送 main、强推历史、打 tag、发布 APK 或顺手开始下一工单。CI 失败时先诊断根因，不得删测试、放宽审计、修改 baseline 或改 seed 来“变绿”。

### 4.2 Codex Cloud 连续 MVP 模式

只有用户明确要求执行 docs/plans/CLOUD-MVP-EXECUTION.md 时，才允许在一个独立云端分支中连续执行 PR-01B 到 PR-08C。该授权仅把每个工单的人工等待点改成自动 checkpoint；每个 checkpoint 仍须只做一个目标、测试先行、严格自审、形成原子 commit 并更新进度日志。

连续模式不得并行写同一工作树，不得跳过 migration 或全量测试，不得自动 Ready、合并、打 tag、发布。触发执行合同列出的停止条件时，必须停在最后一个已通过 checkpoint，不得靠扩大范围或降低门槛继续。

## 5. 产品目标

文研 App 的目标不是资料堆积，也不是把文学知识机械压成普通闪卡，而是一套离线优先、面向南师大专业课、每天组织“记忆—答题—写作—复盘”的个人备考教练。

最终闭环应当是：

1. 今日页明确告诉用户今天该学什么；
2. 到期复习优先，按 FSRS 和学习单元调度；
3. 知识点提供回忆、答题骨架、理解辨析、来源核对四层内容；
4. 真题要求先输出关键词或提纲，再显示核对框架；
5. 610 写作可以离线完成审题、提纲、正文、自评和草稿恢复；
6. 复盘把漏项、错因和写作弱项转成下一次任务；
7. AI 只作为可选的结构化反馈，不成为正式内容来源。

## 7. PR-01A 总合同

PR-01A 的正式边界见 docs/plans/PR-01A.md。其核心要求如下：

- 对正式 seed 只读，不自动修复、不重写、不排序回写；
- 校验 JSON 结构和明确版本的 schema；
- 统计知识点、真题、论述题、写作材料、来源、考频、年份、题型、分值和显式关联；
- 稳定识别重复 ID、旧 ID 删除、悬空 ID 引用、非法 JSON/schema、AI 草稿进入发布内容、OCR 广告噪声和跨科异常；
- 以排序稳定、无动态时间戳的 JSON 生成报告；
- baseline 只记录当前已有债务；新增债务、删除旧 ID 和数量恶化必须失败；
- 通过恶意 fixture 证明失败路径；
- 两次审计报告必须字节完全一致；
- seed 文件内容和 SHA-256 必须保持不变。

PR-01A 已按本总合同完成并由 PR #13 合并：新增只读审计 CLI、版本化 schema、确定性 baseline、最小 fixture 和回归测试；正式 seed、Android 产品代码、Gradle、CI 和用户数据均未修改。合并 commit 为 205eb5c2ded5451e461167c7462f2e6348f76bd1。下一阶段是 PR-01B，正式合同见 docs/plans/PR-01B.md。

## 8. 未来实施的回滚和停工规则

- 审计发现 seed 与当前模型不一致时，先保留报告和 fixture，停止扩大 schema 兼容范围；
- 发现既有 ID 删除或关联语义不确定时，禁止自动修复，等待人工确认；
- 需要新增内容来源、正式答案或产品决策时，停止当前 PR；
- 任意数据库变更若不能证明旧用户记录完整保留，退回设计阶段；
- 任何实现若需要修改超出当前工单允许目录的文件，先报告并等待授权；
- 代码 PR 回滚应优先回滚该 PR 的单一提交或合并提交，不删除历史 tag，不重写 main。

## 9. 每个阶段的最低证据

文档阶段至少有：

- 事实命令和统计口径；
- 有效链接和 Markdown 结构检查；
- git diff --check；
- 修改文件仅在允许目录。

审计阶段至少有：

- 定向单元测试；
- 正式 seed 审计；
- 两次报告字节比较；
- seed SHA-256 前后相同；
- 恶意 fixture 稳定失败。

数据库阶段至少有：

- 新 schema；
- 旧版本链式 migration test；
- 用户记录保留断言；
- ID 集合前后相同。

产品阶段还要增加 Compose、导航、横屏、进程恢复或真机证据。报告必须区分“未运行”“运行失败”“运行通过”，不能把未运行写成通过。
